# 01. プロダクト要求定義書 — kakeibo

夫婦2人用の家計簿WebアプリMVP。本書は「何を・なぜ作るか」を定義する。実現方式は [03_tech_spec.md](./03_tech_spec.md)、画面・APIの詳細は [02_functional_design.md](./02_functional_design.md) を参照。

## 1. 背景・目的

現在、妻がレシートを目視で確認し、各品目を「子ども費」「夫婦生活費」の2項目に手作業で振り分けて集計している。この集計結果は夫婦間の月次費用分担（精算）の根拠として使われるが、レシート1枚ごとの目視分類・電卓集計は時間がかかり、負担が大きい。

本プロダクトの目的は、この手作業を以下のフローで置き換えることである。

| 現状（手作業） | 置き換え後 |
|---|---|
| レシートを目視で品目ごとに分類 | 撮影→AI解析で品目・金額・分類の候補を自動生成 |
| 電卓・メモで月次集計 | ダッシュボードで日次・月次の自動集計 |
| 集計結果をもとに夫婦で精算 | 集計値の確認まではアプリ、精算行為自体は従来どおり手動 |

なお光熱費・ネット代は精算対象外の固定費として扱っており、本アプリには登録しない。

## 2. ユーザーと利用環境

| 項目 | 内容 |
|---|---|
| ユーザー | 夫婦2人のみ（アカウント分離なし、共有パスコードで利用） |
| デバイス | iPhone の Safari（モバイルファースト。PC利用は想定するが最適化しない） |
| 主な利用シーン | 買い物直後、その場でレシートを撮影して登録する。帰宅後にまとめて登録する場合もある |
| 副次シーン | 月末に夫婦のどちらかがダッシュボードで月次合計を確認し、精算する |
| 利用頻度 | 週数回の買い物ごとに1〜3枚程度。年間約500枚を想定 |

## 3. ユースケース

### UC1: レシート登録

1. ユーザーが買い物直後にアプリを開き、レシートをカメラで撮影（または写真を選択）する
2. アプリが画像を解析し、店名・日付・品目一覧（品目名/金額/カテゴリ候補）を表示する
3. ユーザーが同一画面で内容を確認し、誤りを修正する（日付/店名/品目名/金額の編集、品目ごとの3択カテゴリ切替、行の追加・削除）。カテゴリ小計はライブ表示される
4. ユーザーが保存し、登録完了となる（レシート画像と品目データはこの保存操作で初めて保存される。確認画面を離脱した場合は画像も残らない）

レシート紛失時は「手入力で登録」から画像なしで確認・修正画面を開き、日付・店名・品目を入力して保存できる（FR-8）。

### UC2: 月次確認（手動精算）

1. 月末に夫婦のどちらかがダッシュボードを開く
2. 対象月に切り替え、「子ども費」「夫婦生活費」のカテゴリ別合計と日次推移グラフを確認する
3. 合計金額をもとに、夫婦間の精算を従来どおり手動で行う（精算額の計算・記録はアプリ対象外）

### UC3: CSVエクスポート

1. ユーザーがダッシュボードからCSVリンクを開く
2. 指定月または全期間の品目単位データ（レシートID・日付・店名・品目・金額・カテゴリ）をCSVとしてダウンロードする
3. Excel等で開き、検算や独自の分析に使う

## 4. 機能要件

| ID | 要件 | 補足 |
|---|---|---|
| FR-1 | レシート画像をアップロードし、店名・日付・品目一覧（品目名/金額）を自動抽出できる | 抽出はAIによるドラフト生成であり、確定はFR-3のユーザー確認による |
| FR-2 | 各品目を 子ども費(child) / 夫婦生活費(couple) / 対象外(excluded) の3カテゴリに品目単位で分類できる | AIが候補を提示し、ユーザーが上書きできる。値引き・ポイント利用行は負数または excluded で扱える。AIが分類ルールで判断できなかった品目は `uncertain` フラグ付きで提示し、確認画面で「要確認 N 件」＋黄色ハイライトとして目立たせる |
| FR-3 | 保存前に必ず確認・修正画面を経由する（自動保存はしない） | 日付/店名/品目名/金額の編集、カテゴリ3択切替、行追加・削除、カテゴリ小計ライブ表示。品目合計とレシート合計の不一致は警告表示する |
| FR-4 | 日次・月次のカテゴリ別合計を集計・表示できる | 月切替が可能。月次合計が精算の根拠となる |
| FR-5 | 月次ダッシュボードにカテゴリ合計カードと日次積み上げ棒グラフを表示できる | 対象カテゴリは child / couple（excluded は集計対象外） |
| FR-6 | 品目単位のデータをCSVエクスポートできる | 列: receipt_id, date, store, item, price, category。行は日付昇順（同日は receipt_id 昇順・品目順）。月指定または全期間。Excelで文字化けしない形式。画像ありの場合は `receipt_id` と `date` によりS3上のレシート画像原本（`receipts/YYYY/MM/<receipt_id>.jpg`・`YYYY/MM` はレシート日付の年月）と対応付けられる（バックアップ手段を兼ねる） |
| FR-7 | 登録済みレシートを一覧から削除できる | 誤登録のリカバリ用。品目行も併せて削除する |
| FR-8 | レシート画像なしで手入力登録できる（レシート紛失時） | 「手入力で登録」から確認・修正画面を開く。画像なしで保存し、S3 オブジェクトは作らない |
| FR-9 | 共有パスコードによるログイン認証を備える | 未認証時、APIは拒否・画面はログインへ誘導。死活監視用エンドポイントのみ認証不要 |

## 5. 非機能要件

| ID | 要件 | 補足 |
|---|---|---|
| NFR-1 | 運用コストは月額ほぼ0円であること | クラウド無料枠・AI API無料枠の範囲内で運用する |
| NFR-2 | 家族以外の第三者がアクセスできないこと | 推測困難なパスコード＋改ざん検知可能なセッションで保護する。パスコードは**12文字以上のパスフレーズ**とする（文字種の混在は強制せず、長さのみ起動時に検査して警告する）。ログイン試行回数制限・ロックアウトは設けない（決定 2026-09-12。利用者2人のため締め出し事故の方が現実的なリスク。根拠は 02 §6.1 / 03 §6） |
| NFR-3 | レシート1枚の解析〜保存が概ね1分以内に完了すること | 買い物直後に「その場で登録し終えられる」体感速度 |
| NFR-4 | 単一リージョン構成でよい | 東京リージョン想定。冗長化・DR は不要 |
| NFR-5 | SLAは設けない | 家庭内利用のため、一時的な障害・メンテ停止は許容する |
| NFR-6 | 登録データ（レシート画像・品目データ）は夫婦のみが参照できること | 外部共有機能は持たない |

## 6. 対象外（スコープ外）

- 光熱費・ネット代などの固定費の登録（精算対象外のためアップロードしない）
- 精算額の自動計算（誰が誰にいくら払うか）・精算履歴の記録
- ネイティブアプリ（iOS/Androidアプリ）。Webアプリのみ
- 複数世帯・複数アカウント対応（ユーザー管理機能）
- レシート以外の入力の自動化（銀行・クレカ明細連携、口座同期等）

## 7. 未決事項

| ID | 事項 | 対応方針 |
|---|---|---|
| OPEN-1 | 曖昧品目の分類ポリシー（例: 子どもも食べるお菓子、家族共用の食材など child/couple の境界が曖昧な品目） | **暫定決定（2026-09-12）・暫定ルール適用中**。child=ベビー・子ども向けと分かるもの（ベビー向け消耗品／ベビー向け雑貨／子ども向け衣類。アカチャンホンポ・西松屋・バースデイ等のベビー専門店のレシートは品目名が読めなくても child に倒す）、couple=家族で使うもの全般（食材・酒・日用品・外食など。酒は食費扱い）、excluded=個人の買い物（服・本・趣味のためのもの・雑貨）。判断できない品目は couple を既定とし `uncertain` フラグを立てて確認画面で強調する（02 §5.2）。確定版の具体例リストは **Phase B の最終ステップ**で実レシート2〜3枚を実 Gemini API に通して精緻化する（手動スモーク `scripts/smoke_gemini.py`。Phase B の完了条件。03 §1 / 02 §5.2。Gemini API キーの発行が前提）ため、本項目は OPEN のまま残す |
